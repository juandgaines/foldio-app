# System design conventions

Every `sd-*` skill reads this file before it starts. It is the contract between the steps: no skill calls another skill. Each one reads what earlier steps left here, writes its own files, and ends by naming the next step.

## The sequence

| Step | Run | Writes |
|---|---|---|
| 1 | `sd-problem` | `SOURCES.md`, `REQUIREMENTS.md`, `QUESTIONS.md` |
| 2 | `sd-api` | `API.md`, `openapi.yaml` if the API is designed here, ADRs for API choices |
| 3 | `sd-architecture` | `architecture.json`, `graph.json` (chunks), generated `ARCHITECTURE.md`, `GRAPH.md`, `architecture.html` |
| 4 | `sd-slice <chunk>` | `chunks/<chunk>.md`, the chunk's changes in `graph.json` |
| 5 | `sd-deep-dive <change>` | `changes/<change>.md`, ADRs, rows in `DECISIONS.md`, L3 components in `architecture.json` |
| 6 | `/opsx:propose <change>`, then `openspec validate <change> --strict` | `openspec/changes/<change>/` |
| 7 | `/opsx:apply` | One PR per task group |
| 8 | `/opsx:verify <change>`, in a new session | A report in chat |
| 9 | `sd-verify <change>` | `verify/<change>.md` |
| 10 | `/opsx:archive <change>` | Updated `openspec/specs/` |

Steps 1 to 3 run once (again when the scope changes). Step 4 runs once per chunk. Steps 5 to 10 run once per change. `python3 docs/architecture/tools/graph.py --ready` lists the changes that can start now.

## Files

```
docs/architecture/
  CONVENTIONS.md     this file
  LOG.md             every run of every step: what was found, what the user answered
  SOURCES.md         every source read, its link, and the given facts it provides
  REQUIREMENTS.md    R ids
  QUESTIONS.md       Q ids: answered questions, open questions, conflicts
  API.md             the contract: given, gaps, conflicts
  openapi.yaml       only when the API is designed in this project
  DECISIONS.md       D ids: given facts, open decisions, decided decisions
  architecture.json  the C4 model, data, trust zones, responsibilities (source of truth)
  graph.json         chunks and changes with dependencies (source of truth)
  ARCHITECTURE.md    generated by tools/graph.py. Never edit by hand
  GRAPH.md           generated by tools/graph.py. Never edit by hand
  architecture.html  generated by tools/graph.py. Open it in a browser
  chunks/<chunk>.md  the change plan of one chunk
  changes/<change>.md  the deep dive of one change, input for /opsx:propose
  verify/<change>.md   the verification report of one change
  tools/graph.py, tools/viewer.html
docs/adr/
  TEMPLATE.md
  NNNN-<slug>.md
```

## Given, conflict, open

Every fact goes in one of three buckets, and the bucket stays visible in every file:

- **Given:** a source fixes it. Cite the source: file, URL, endpoint, frame, or "user answer, LOG.md <date>". Given facts are never reopened.
- **Conflict:** two sources, or two parts of one source, disagree. Quote both sides. Never resolve a conflict yourself. The user marks it Clarify (ask the source's owner) or Open (the team decides).
- **Open:** no source answers it. It is a decision for the team.

## IDs

IDs are stable. Never renumber or reuse one; mark it Dropped instead.

| Prefix | Meaning | Example |
|---|---|---|
| R | Requirement | R12 |
| Q | Question or conflict | Q4 |
| D | Decision | D7 |
| Element id | An element in `architecture.json` | `android`, `file-store` |
| Chunk id | `cNN-<name>` | `c03-crypto-core` |
| Change id | `cNN-MM-<name>` | `c03-01-key-derivation` |
| ADR | `NNNN-<slug>.md` in `docs/adr/` | `0004-chunk-nonce-and-aad.md` |

## Slicing

- **Chunk:** one capability ("Upload files") or one foundation ("Crypto core"). Chunks are vertical: sliced by capability.
- **Change:** one OpenSpec change. One behavior that works end to end and can be tested through its scenarios. Changes are vertical and thin.
- **Task group:** one layer of one change. Task groups are horizontal: Domain first, then Data (one group per data source), then Presentation (one group per screen). Platform-heavy groups split into Android and iOS.
- **PR:** one task group.

Foundation chunks (crypto, database, network client, design system) are horizontal on purpose. Each foundation change names the vertical change that uses it next.

## Sizing rules for a change

- One behavior, in one capability spec, with 2 to 6 scenarios.
- At most one decision stop.
- 3 to 6 task groups, each one PR under 400 changed lines.
- It can be tested without later changes.
- Its dependencies on other changes are named.

When a change breaks a rule, split it. Usual split points: a second decision stop, a second capability, a platform-specific part.

## Decision stops

A decision stop is a choice that has more than one reasonable answer, is hard to change later, and is not a given fact. Typical stops: where data lives on disk, a byte format on disk or on the wire, key handling, background execution, concurrency control, the source of truth for lists, caching and eviction, plaintext exposure, a library that shapes the code, a different answer per platform.

At a stop the mentee writes an ADR in `docs/adr/` from `TEMPLATE.md`, then keeps going. Code does not wait for approval. The reviewer reviews the ADR together with the PR.

## Rules every skill follows

1. Read this file first. Check that the inputs you need exist. If one is missing, stop and name the step that creates it.
2. Never answer an open question or an open decision for the user. Show the options and their trade-offs. The user picks.
3. Ask with `AskUserQuestion` when the answer has natural options: up to 4 questions per call, 2 to 4 options each. Batch related questions. Never re-ask what is in a source, the repo or `LOG.md`.
4. Write to `LOG.md` the moment something is found or answered: date, step, what, source.
5. Never edit generated files. Change `architecture.json` or `graph.json` and run `python3 docs/architecture/tools/graph.py`.
6. Subagents are allowed only for work that needs no answer from the user: reading a large source, or an independent review.
7. End with a short summary and the next step, for example: "Next: run `sd-slice c03-crypto-core`."
